# Agent App Testing

รายละเอียดของ **step 6 ("สำรวจแอปจริง")** ใน skill `qa-automate-readiness` เฉพาะกรณีที่เลือกใช้ **agent (subagent)**
เป็นคนไปเทส/สำรวจแทนคนหรือแทนสคริปต์ที่รันเอง — ไม่ใช่ workflow gate เอง (ดู `qa-automate-readiness` สำหรับภาพรวม)

## หลักการ

Agent ที่ไปเทสแอปจริงมีความเสี่ยง 2 แบบที่ต่างจากการเทสมือ:
1. **ทำงานเยอะและเร็วกว่าคน** — ถ้าขอบเขต/กฎความปลอดภัยไม่ชัดตั้งแต่ต้น อาจสร้าง/แก้/ลบข้อมูลจริงในระบบที่ใช้ร่วมกันทั้งทีมไปไกล
   ก่อนจะรู้ตัว (ต่างจากคนเทสมือที่จะสังเกตเห็นความผิดปกติและหยุดเองได้เร็วกว่า)
2. **เชื่อข้อความที่ UI/API ตอบกลับตรง ๆ โดยไม่ตรวจสอบซ้ำ** — ถ้า UI แสดงผลผิดจากที่ backend ทำจริง (เจอเคสจริงแล้ว —
   ดู "บทเรียนจริง" ด้านล่าง) agent จะสรุปผลผิดและรายงานเป็นเท็จ ทำให้ข้อสรุปทั้งชุดใช้อ้างอิงต่อไม่ได้

## ก่อน dispatch agent — ต้องขอบเขตความปลอดภัยจากผู้ใช้ก่อนเสมอ

**ถามผู้ใช้ก่อนทุกครั้ง** (อย่าเดาเอง) ว่า TC/งานไหนปลอดภัยให้ agent ทำอัตโนมัติ กับไหนต้องขอ authorize แยก — โดยทั่วไป:

- **ปลอดภัย (agent ทำได้เอง):** สร้าง/แก้/ลบเฉพาะ test data ที่ agent สร้างขึ้นเองเท่านั้น, การดูข้อมูลจริงแบบ read-only
  (ไม่แก้ไข/ไม่ลบ), การยิง API ที่คาดว่าจะถูกปฏิเสธ (เช่น เทส permission enforcement) ไปยัง ID ปลอมหรือ resource ที่ agent
  สร้างเอง เพื่อไม่ให้กระทบของจริงไม่ว่าผลจะออกมาทางไหน
- **ต้องขอ authorize แยกก่อนเสมอ (ห้ามให้ agent ตัดสินใจเอง):** operation ที่กระทบข้อมูลจริงวงกว้าง (เช่น migration/sweep
  ทั้งระบบ), การแก้ไข/ลบ service account หรือ resource ที่ระบบอื่นพึ่งพา, การทดสอบกับบัญชีจริงของคนใดคนหนึ่งโดยเฉพาะ
  (ต้องถามเจ้าของบัญชีก่อนเสมอแม้จะเป็น dev/test environment)
- ตั้งชื่อ test data ที่ agent สร้างให้มี prefix ชัดเจนแยกจากข้อมูลจริงได้ทันที (เช่น `qa-<requirement-id>-*`)
  เพื่อให้ตรวจสอบ/cleanup ย้อนหลังได้ง่าย

## วิธี brief agent

- ให้บริบทครบ: เป้าหมายงาน, ไฟล์ TC/draft ที่ต้องอ้างอิง, ขอบเขตที่อนุญาต/ไม่อนุญาตแบบระบุ ID ชัดเจน (ไม่ใช่คำอธิบายกว้าง ๆ)
- แปะ **ข้อเท็จจริงเกี่ยวกับหน้าจอ/ระบบที่สำรวจไว้แล้ว** ลงในบรีฟ (เช่น เส้นทางเมนู, locator ที่ใช้ได้, โครงสร้าง modal,
  ชื่อ field/ปุ่มจริง) เพื่อประหยัดเวลาไม่ต้องให้ agent สำรวจซ้ำจากศูนย์ — **ต้องดึงมาจากการ์ด Linear/ไฟล์ TC เก่าที่เคยทดสอบ
  requirement เดียวกันหรือหน้าจอเดียวกันมาก่อนจริงด้วยเสมอ** (ไม่ใช่แค่โน้ตที่จำไว้เองในเซสชัน) เช่น selector ที่ใช้ได้จริง,
  บั๊กที่เคยเจอซ้ำ (เช่น toast error ข้อความผิดตอนสร้าง user), quirk ของ DOM (เช่น table header อยู่ใน `tbody`) — ค้นจาก
  `list_issues`/`get_issue` ของ TC เดิมในโครงสร้างเดียวกัน หรือไฟล์ผลเก่าใน repo ก่อนเริ่ม flow ใหม่ทุกครั้ง
- สั่งให้ agent **บันทึกผลลงไฟล์ทันทีหลังทดสอบแต่ละ TC เสร็จ** ไม่ใช่รอไปบันทึกรวมตอนจบ (กัน context ยาวเกินไปแล้วผลหาย)
- สั่งให้ agent เขียน script ชั่วคราวไว้ใน `temp_scripts/` (หรือโฟลเดอร์ temp ที่โปรเจกต์กำหนด) แล้ว**ลบทิ้งเมื่อทำงานเสร็จ**
  ตามธรรมเนียมการเก็บ repo ให้สะอาด
- ถ้ามีพฤติกรรมเสี่ยงสูงเป็นพิเศษ (เช่น เทส self-modification prevention กับบัญชีจริงของ admin) ให้สั่งชัดเจนว่า
  **ถ้าพบว่า action ที่คาดว่าจะถูกปฏิเสธกลับสำเร็จจริง ให้หยุดทันทีและรายงานเป็นประเด็นความปลอดภัย** ไม่ใช่ทดสอบต่อเรื่อย ๆ
- รัน agent แบบ **background** เสมอสำหรับงานที่ใช้เวลานาน (หลาย TC) — อย่า poll เช็คผลเอง รอ notification

## รูปแบบ flow การทดสอบ: atomic vs flow เดียวต่อเนื่อง

ก่อนเริ่ม brief agent (หรือก่อน Claude เองลงมือทดสอบแอปจริงตรงๆ) ต้องรู้ก่อนว่า TC ที่จะเทสเป็นโหมด **atomic** หรือ
**flow-style** — มาจากคำตอบ QA ที่ถามไว้ตอนร่าง TC แล้ว (ดู `linear-testcase-writer` → ขั้นตอน ข้อ 2 และ Generation rules
→ Test granularity) ถ้ายังไม่เคยถาม QA มาก่อนตอนร่าง TC ให้ถามตอนนี้ก่อนเริ่มเทส

- **Atomic**: ทดสอบและเก็บหลักฐานแยกต่อ TC ตามปกติ (ตามมาตรฐานเดิมด้านล่าง)
- **Flow-style**: ทุก step ของ flow เดียวกัน (เช่น สร้าง user → เช็ค role → login ครั้งแรก) ต้องอัดวิดีโอเป็น**คลิปเดียว
  ต่อเนื่องตลอด flow** ห้ามแยกเป็นหลายคลิปย่อยตาม step/ตาม script ที่รัน — ถ้าจำเป็นต้องสลับ browser context ระหว่าง flow
  จริงๆ (เช่น ใช้ admin session รีเซ็ตรหัสผ่านก่อน แล้วค่อยเปิด context ใหม่ไป login ด้วย user จริง) ให้พยายามลดจำนวนคลิป
  ให้น้อยที่สุดเท่าที่ทำได้ และถ้าแยกมากกว่า 1 คลิปจริงๆ ต้องระบุเหตุผลทางเทคนิคไว้ในรายงานผลด้วยว่าทำไมแยกไม่ได้

## มาตรฐานการรายงานผลใน Linear (Actual Result)

อ้างอิงสไตล์จากการ์ดตัวอย่างที่ user ชี้ให้ดู (SBH-2513, โปรเจกต์อื่น — ใช้แค่เป็นตัวอย่างสไตล์ตามที่ user สั่งเจาะจง
ครั้งเดียว ไม่ได้เอา business logic/ข้อมูลของโปรเจกต์นั้นมาปน) ปรับใช้ **ภายในโครง template เดิมของ `linear-testcase-writer`
เท่านั้น** (ห้ามเปลี่ยนชื่อ/ลำดับ/ตัด section ตามกฎเดิมของสกิลนั้น — ข้อมูลอ้างอิง, Preconditions, Test Data, Test Steps,
Expected Result, Actual Result, หมายเหตุ ต้องครบเหมือนเดิมทุกใบ):

- ขึ้น `##` heading ให้ทุก section name เดิม (ชื่อเดิมเป๊ะ แค่เปลี่ยนการ render จากข้อความเฉยๆ เป็น markdown heading)
- ใส่สถานะ Pass/Fail ต่อท้าย heading "Actual Result" ตรงๆ เช่น `## Actual Result — Fail` แทนการไล่ bold/emoji ทีละ bullet
- เปิด Actual Result ด้วยบรรทัดสรุปสั้นๆ ว่า step ไหนผ่าน/ไม่ผ่าน/ข้าม ก่อนเข้ารายละเอียด
- ฝังรูป/วิดีโอ **inline ตรงจุดที่เกี่ยวข้องในเนื้อหา** (ไม่ใช่ปล่อยเป็น attachment list ท้ายการ์ดอย่างเดียว) ด้วย syntax:
  - รูป: `<linear-image>{"type":"image","attrs":{"src":"<signed-url>","alt":"<filename>"}}</linear-image>`
  - วิดีโอ: `<linear-embed node-type="video">{"uploadState":"finished","uploadId":null,"src":"<signed-url>","title":"<filename>","size":null,"controls":true,"height":1080,"width":1920,"metadataId":null,"mimetype":null}</linear-embed>`
  - ต้อง**อัปโหลดไฟล์ผ่าน `prepare_attachment_upload` → PUT → `create_attachment_from_upload` ก่อนเสมอ** เพื่อให้ได้
    `<signed-url>` จริงมาใส่ใน tag — ใส่คำบรรยายสั้นๆ ไว้บรรทัดเหนือรูปทุกครั้งว่ากำลังแสดงอะไร (เช่น "ขั้น 4 หลังกด —
    หัวข้อยังพับอยู่ (จุดที่ไม่ผ่าน)")
  - **ยังไม่ยืนยัน 100%** ว่า URL ที่ฝังแบบนี้จะคงอยู่ยาวหรือ re-sign อัตโนมัติเมื่อ Linear เรนเดอร์ซ้ำในอนาคต (สังเกตว่า
    URL ใน `attachments` relation ปกติจะถูก re-sign ใหม่ทุกครั้งที่ `get_issue`, exp สั้นแค่ ~5 นาที แต่ embed ตรงๆ ใน
    body text ไม่ชัดว่า Linear จัดการแบบเดียวกันหรือไม่) — ถ้าเจอว่ารูปที่ฝังไว้ขึ้นเป็น broken image ย้อนหลัง ให้กลับไปใช้
    attachment list ท้ายการ์ดอย่างเดียวแทน แล้วอัปเดต entry นี้

## มาตรฐานการเก็บหลักฐาน

**ทุก TC ต้องมีทั้งภาพและวิดีโอ — ไม่ใช่เลือกอย่างใดอย่างหนึ่ง** (ยืนยันกับผู้ใช้แล้ว 30 ก.ย. 2026 หลังเจอว่า Phase 1 ของ
COR-1724 เก็บแค่ screenshot ให้ 65/67 TC เพราะกฎก่อนหน้านี้เขียนว่า "วิดีโอหรือภาพ" ทำให้เข้าใจว่าเลือกได้)

- โครงสร้างโฟลเดอร์: `.playwright-mcp/<requirement-id>/images/` สำหรับภาพนิ่ง, `.playwright-mcp/<requirement-id>/videos/`
  สำหรับวิดีโอ — แยกชัดเจน ไม่ปนกับ root ของ evidence folder
- **กรอบสีบนภาพ/วิดีโอ** (ยืนยันกับผู้ใช้แล้วว่าใช้แบบนี้ 30 ก.ย. 2026): **กรอบแดง** = จุดที่กำลังกรอกข้อมูล/กดปุ่ม/จุดที่กำลัง
  ตรวจสอบ (รวมถึงผลลัพธ์ที่ผิดคาดในกรณี Fail), **กรอบเขียว** = ผลลัพธ์ที่ยืนยันว่าถูกต้องตรงกับ Expected Result —
  แต่ละกรอบมีป้ายข้อความสั้น ๆ บอกว่ากำลังวงอะไร (เช่น "กรอก: ชื่อบัญชีผู้ใช้งาน", "ผลจริง: ... — SECURITY BUG")
  วาดด้วย `page.evaluate()` สร้าง `<div>` ตำแหน่ง `fixed` ทับ `boundingBox()` ของ element จริง (ต้องเปิดหน้าเว็บจริงเพื่อหา
  ตำแหน่งใหม่เสมอ — วาดทับภาพเดิมที่ไม่มีตำแหน่ง element เก็บไว้จะไม่แม่น)
- วิดีโอ: ใช้ `recordVideo: { dir, size }` ตอนเปิด browser context (playwright-core หรือ `@playwright/test` ก็ได้)
  ปิด context เพื่อ finalize ไฟล์ แล้ว rename ไฟล์ `.webm` ที่ auto-generate ให้ชื่อสื่อความหมาย (เช่น `tc005-video.webm`)

## กฎยืนยันผลจริง (สำคัญที่สุด — อย่าข้าม)

**ห้ามเชื่อข้อความ/response ที่ UI แสดงทันทีเพียงอย่างเดียว** ต้องไปยืนยันสถานะจริงของระบบก่อนสรุปผล Pass/Fail/Gap เสมอ
(เช่น เปิดหน้ารายการ/หน้า detail ดูว่าข้อมูลถูกสร้าง/แก้ไข/ลบจริงไหม) — **ถ้าต้องไปดูอีกหน้าเพื่อยืนยัน วิดีโอ/หลักฐานต้อง
อัดต่อเนื่องจนจบการยืนยันนั้นในคลิปเดียว ห้ามตัดจบแค่จุดที่เห็นข้อความ/response แรก** เพราะผลที่บันทึกไว้จะถูกเอาไปอ้างอิง
แปะใน test case จริงในอนาคต ต้องเป็นหลักฐานที่ตรวจสอบย้อนกลับได้ครบ (rule นี้ sync คู่กับ `qa-automate-readiness` step 6
— แก้ที่ไหนต้องแก้อีกที่ให้ตรงกันด้วย)

### บทเรียนจริง (COR-1724, 30 ก.ย. 2026)

ทดสอบสร้าง staff account ใหม่ — UI ขึ้น toast แดง "ระบบไม่ได้รับสิทธิ์...กรุณาติดต่อผู้ดูแลระบบ" (API ตอบ 403) ทำให้ดูเหมือน
ล้มเหลวชัดเจน แต่พอเข้าไปดูหน้ารายการ user จริง **account ถูกสร้างสำเร็จจริงทุกครั้ง** (enabled=true, มี credential ตั้งไว้จริง)
— agent ที่เชื่อแค่ข้อความ toast รายงานผลว่า "สร้างไม่ได้ บล็อกการทดสอบ ~24 TC ที่ต้องมี test account ใหม่" ทั้งที่ความจริงคือ
"สร้างสำเร็จ แต่ระบบแจ้งข้อความผิด" ซึ่งเป็นบั๊กคนละแบบและร้ายแรงกว่าที่เข้าใจตอนแรกมาก (แอดมินจริงจะเข้าใจผิดว่าไม่มีอะไรเกิดขึ้น
แล้วอาจกดสร้างซ้ำเรื่อย ๆ) กว่าจะจับได้ต้องเปิดไปเช็คหน้ารายการ user เองหลังจากนั้น

### บทเรียนจริง (COR-1724, 14 ต.ค. 2026) — หน้าขาวว่างเปล่าหลัง login คือปัญหา navigation/timing ไม่ใช่บั๊กจริง

เคยเจอซ้ำหลายรอบ (TC-001, TC-002, TC-018): หลัง OAuth redirect กลับมาที่ `https://dev-x.cortexcloud.co/cortex#state=...`
สำเร็จ (URL ถูกต้อง, ไม่มี console error) หน้าเว็บกลับเป็นจอขาวค้าง ไม่ render อะไรเลย (`document.getElementById('root').innerHTML`
= 0) ตอนแรกสงสัยว่าเป็นบั๊กจริงหรือ artifact ของ automated browser เพราะหา root cause ไม่เจอ (ลอง reload/รอนานขึ้นก็ไม่ช่วย)

ผู้ใช้ชี้ทางแก้: **เป็นปัญหา performance ของระบบที่โหลดช้า ไม่ใช่บั๊ก** — วิธีแก้คือหลัง login เสร็จ ให้ `goto()`
ไปที่ `https://dev-x.cortexcloud.co/cortex/apps` ตรง ๆ (ไม่ใช่รอที่หน้า bare redirect landing) พร้อมเพิ่ม delay ให้มากขึ้น
