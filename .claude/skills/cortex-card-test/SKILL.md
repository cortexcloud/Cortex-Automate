# ทดสอบการ์ดตาม TC ใน Sub-Issue แล้วแนบผลลง Linear

สกิลนี้เก็บ**ลำดับงาน**ที่ผู้ใช้สั่งเมื่อ 6 ต.ค. 2026 (การ์ด SBH-2394):
"ช่วยทดสอบการ์ด … เล่นตาม Test Case ที่มีอยู่ใน Sub Issue แล้ว … แนบผลการทดสอบ โดยเป็นรูปและคลิป … ถ้าสงสัย … ถามได้เลย และเก็บเป็น Skill ไว้ด้วย"

กฎของโปรเจกต์ (R1–R44) · โครงสร้างไฟล์ · คำสั่ง · ความรู้หน้าจอ อยู่ในสกิล `cortex-automate` — **โหลดก่อนเริ่ม** แล้วทำตามนั้นเมื่อขัดกับไฟล์นี้
**ทุกขั้นในลำดับงานด้านล่าง แจ้งสถานะผู้ใช้เป็นระยะ (R44)**: ก่อนเริ่มขั้น · ทันทีที่ติดปัญหา (ติดอะไร กำลังแก้อย่างไร) · เมื่อจบขั้น — ไม่ทำเงียบยาวแล้วสรุปตอนจบ
งานจบแล้วมีอะไรเปลี่ยน (ขั้นตอน / กับดัก / คำตอบของผู้ใช้) → แก้ไฟล์นี้ และลงประวัติท้ายไฟล์

---

## ลำดับงาน

### 1) อ่านการ์ดและ Sub-Issue ให้ครบก่อน

- `get_issue` การ์ด (+ `includeRelations`) · `list_comments` · รูปในการ์ดเปิดด้วย `extract_images` (การ์ดบางใบมีแค่รูป)
- ไล่ Sub-Issue ด้วย `list_issues parentId=…` ทีละชั้น: การ์ด → `EXE - CT - …` → `SC-00x` → `TC-00x` แล้ว `get_issue` ทุก TC (รายการแบบ list ตัดคำอธิบาย)
- ใต้การ์ดอาจมีสเปกของ dev (เช่น "Spec: …") — อ่านด้วย บอกพฤติกรรมจริง / ชื่อ component / สิทธิ์ / สิ่งที่อยู่นอก scope
- คำอธิบายของ EXE สำคัญที่สุด: **Pre-condition** · **Scope ของชุด** · **ข้อควรรู้ก่อนรัน** · **ยังไม่ทำในชุดนี้** · ระบบที่รันได้ (Dev-X / SBH Prod)
- TC ของชุดอื่นที่ EXE อ้างถึง เปิดดูผลเทสมือ (มีคลิปเดิมของผู้ใช้) ไว้ดูว่าผู้ใช้ลงผลหน้าตาแบบไหน

### 2) ตรวจว่า TC ครอบคลุมไหม (R16)

- จับคู่บรรทัดในการ์ดกับ TC · เคสที่ EXE จดไว้ว่า "ตกลงยังไม่ทำ" **ไม่ต้องเสนอซ้ำ** แค่บอกว่ารู้
- มีช่องว่างจริงค่อยเสนอ TC ในแชท (ผู้ใช้ตัดสินว่าจะเพิ่มลง Linear ไหม)

### 3) ตรวจว่ารันที่ระบบไหนได้ — เริ่มที่ dev-x แบบอ่านอย่างเดียว

ทำได้เลยไม่ต้องถาม (dev-x เป็นระบบตั้งต้น):
- ฟีเจอร์ขึ้นระบบหรือยัง: โหลด `/cortex/` หาชื่อ `assets/index-<hash>.js` แล้ว grep ชื่อ component / สิทธิ์จากสเปก (ข้อความไทย grep ไม่เจอ · เลข `APP_VERSION` เชื่อไม่ได้)
- มีข้อมูลตาม Pre-condition ไหม: สคริปต์ node ใน scratchpad ขอ token ด้วย password grant (`cortex-ui`) แล้ว `GET` API ที่เกี่ยวข้อง — อ่านอย่างเดียว ไม่พิมพ์รหัสผ่าน / token
- dev-x รันไม่ได้ → เก็บเหตุผลเป็นตัวเลข (API ตอบอะไร · ตรวจกี่รายการ) ไว้ลงช่อง Test Result ของ Dev-X

**SBH Prod ยังห้ามแตะจนกว่าผู้ใช้อนุญาตสำหรับการ์ดนั้น** (R40 — การอนุญาตของการ์ดก่อนใช้กับการ์ดใหม่ไม่ได้)

### 4) ส่งสรุป + แผน แล้วถามครั้งเดียว

ข้อความเดียว: สรุปการ์ด · ผลตรวจ TC · ผลตรวจ dev-x · แผน แล้วถามด้วย `AskUserQuestion` (ตัวเลือกแนะนำไว้ข้อแรก) เฉพาะเรื่องที่เป็นของผู้ใช้:

| เรื่อง | ถามเมื่อ | คำตอบที่ผ่านมา |
|---|---|---|
| ระบบที่รัน | dev-x รันไม่ได้ ต้องใช้ SBH Prod | SBH-2394: "รันบน SBH Prod" · SBH-2391: ผู้ใช้ระบุ Dev-X มาในคำสั่ง (ไม่ต้องถาม) · SBH-2471: ผู้ใช้ระบุ Prod มาในคำสั่ง → ตรวจ Prod แบบอ่านอย่างเดียวได้เลย (บอกก่อนทำ) แต่**การสร้างข้อมูลบน Prod ยังต้องถาม** |

| ลงผลใน Comment (การ์ดบั๊กไม่มี TC) | ผู้ใช้สั่ง "ลงผลใน Comment ใช้ตัวอย่าง Comment ก่อน" | SBH-1699 (14 ต.ค. 2026): ใช้รูปแบบ Comment ของผู้ใช้บนการ์ดเดียวกัน — `Env : SBH Prod` · `Date : 14/10/2569` (วัน/เดือน/พ.ศ.) · `Result : Pass` · `Result Test: <สิ่งที่ทำ>` + คลิป 1 ไฟล์ฝัง `![ชื่อ.webm](assetUrl)` (ไม่มีภาพ · ไม่สร้าง attachment ของ issue) · บรรทัดคั่นด้วยบรรทัดว่าง · สถานะ: "ลง Comment อย่างเดียว ไม่เปลี่ยนสถานะ" · ข้อมูล Prod: "สร้าง 1 ราย + เปิด Visit ทิ้งไว้" (ไม่ปิด Visit — ต่างจากการ์ดก่อนๆ) |

| TC ไม่ผ่าน | เทสไม่ผ่านตาม Expected บนระบบที่ผู้ใช้สั่ง (ตรวจซ้ำแล้วว่าไม่ใช่สคริปต์) — ถามพร้อมผลจริงว่าลงผลแบบไหน | SBH-2442 (Dev-X · ยังไม่รู้ว่าตัวแก้ขึ้น Dev-X หรือยัง · Claude แนะนำให้เทียบไฟล์ของ Prod ก่อน): **"ลง Fail + สถานะ Failed"** → ลง Fail ใต้หัวของระบบที่รัน + คลิป / ภาพถึงจุดที่ไม่ผ่าน + สถานะ `Failed` · ไม่แตะ Prod · เขียนในผลว่ายังไม่ได้ตรวจเรื่องตัวแก้ (R46) |

เรื่องที่ไม่กระทบการเขียน / รันเทส (แนบผลที่ไหน · ผลของ Expected ที่ก้ำกึ่ง) ถามหลังรันเสร็จได้ จะได้ถามพร้อมผลจริงครั้งเดียว (ทำแบบนี้รอบ SBH-2391) · ผู้ใช้สั่ง "แนบผล" มาตั้งแต่ต้น = ใช้รูปแบบในข้อ 7 ได้เลย (การตีความของ Claude — ผู้ใช้ยังไม่ได้ยืนยันว่าเป็นค่าถาวร) · เรื่องอื่นที่ตัดสินเองได้ (ชื่อไฟล์ โครง spec) ไม่ต้องถาม

### 5) สำรวจหน้าจอ แล้วเขียน spec

- บอกผู้ใช้ก่อนทุกครั้งว่าจะรันอะไรบนระบบไหน (R31) และรัน**เปิดจอ** (`--headed`)
- สำรวจด้วยเทสชั่วคราวอ่านอย่างเดียว `mock-data/_explore-<เลขการ์ด>.spec.ts` (dump `outerHTML` / `innerText` / ภาพ ลง `.cache/`) — พังแล้วอ่าน `error-context.md` (มีโครง role ของทั้งหน้า) · **ลบไฟล์เมื่อเขียน spec จริงเสร็จ**
  - ดูให้ออกก่อนว่าปุ่มไหนเขียนข้อมูล (เช่น `รับผู้ป่วยเข้า ER`, `ยืนยันผู้ป่วยมาถึงแล้ว`) แล้วเขียนกำกับใน helper ว่าห้ามกด
  - ไฟล์ที่เพิ่งแก้ด้วย `sed` / heredoc ต้อง Read ก่อนใช้ Write ทับ ไม่งั้น Write ถูกปฏิเสธแล้วเทสเก่ารันซ้ำ
- spec จริง: `tests/modules/<โมดูล>/SBH-<เลข>-<ชื่อ>.spec.ts` (R9: 1 เทส = 1 flow · step ชื่อ `TC-00x (SBH-xxxx) ขั้น n …` · tag เลขการ์ด + เลข TC) · ส่วนใช้ซ้ำไว้ `helpers/`
  - ต้องรันบน Prod → import `test` จาก `mock-data/fixtures` (กันไฟล์แอปโหลดไม่ผ่าน) · เพิ่มไฟล์ใน `testMatch` ของ `playwright.sbh-prod.cards.config.ts` · ระบบที่รันไม่ได้ให้ `test.skip` พร้อมเหตุผล
  - เทสอ่านอย่างเดียว: จด request ที่เป็น PUT / PATCH / DELETE / graphql mutation ลง annotation ไว้ยืนยันว่าไม่ได้เขียนอะไร
  - เลือกข้อมูลเองจาก API ตาม Pre-condition (ไม่ฝังเลข HN) + env ไว้เจาะจง · บน Prod ใช้เฉพาะผู้ป่วย Mock
