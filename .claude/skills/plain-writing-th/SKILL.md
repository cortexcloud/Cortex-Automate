# Plain Writing TH

เป้าหมาย: คนอ่านเข้าใจได้ในการอ่านรอบเดียว และงานเขียนหน้าตาเหมือนกัน ไม่ว่า agent ตัวไหนเป็นคนเขียน

## ใช้เมื่อไหร่

ทุกครั้งที่เขียนข้อความให้คนอ่าน:

- คำตอบ สรุปผล คำถาม และตัวเลือกใน chat
- เอกสาร, slide, report, แผนงาน
- การ์ด Linear (bug, test case, EXE)
- TODO.md
- content ที่ใส่ลงไฟล์ ระบบ หรือหน้าจอ เช่น ข้อความบน UI, ข้อความ error, เนื้อหาในเอกสาร

**ไม่ใช้กับ** (ปล่อยให้เป็นไปตามของเดิม):

- **ทุกอย่างที่เป็นของ repo** — commit message, PR description, code comment, README และเอกสารใน repo ให้ตาม convention ของ repo นั้น skill นี้ไม่เข้าไปกำหนด
- **ข้อความ UI ที่ทีมหรือโปรเจกต์มีมาตรฐานอยู่แล้ว** — ใช้มาตรฐานของทีม skill นี้ใช้เฉพาะตอนที่ไม่มีมาตรฐานของทีม
- code, ชื่อตัวแปร, ชื่อ field, path, คำสั่ง
- ข้อความที่ต้องสะกดตรงกับหน้าจอหรือระบบจริง
- งานที่ผู้ใช้สั่งภาษาอื่นไว้ชัดเจน

**เมื่อมี skill เฉพาะทาง** (เช่น `qa-bug-writer`, `linear-testcase-writer`): skill เฉพาะทางกำหนด **โครง** ส่วน skill นี้กำหนด **ภาษา** ถ้าขัดกัน ให้โครงตาม skill เฉพาะทาง และภาษาตาม skill นี้

## ก่อนเขียน ตอบ 3 คำถามนี้

1. **ใครอ่าน** — ผู้ใช้เอง, หัวหน้า/PO, dev, หรือผู้ใช้ปลายทางบนหน้าจอ → ใช้กำหนดว่า technical ได้แค่ไหน
2. **เขาต้องได้อะไร** — รู้ผลลัพธ์, ตัดสินใจ, หรือลงมือทำต่อ
3. **หลักฐานคืออะไร** — ทุกข้อสรุปและตัวเลขมีข้อมูลจริงรองรับหรือไม่

## กฎภาษา

1. **ไทยเป็นหลัก ศัพท์ technical เป็นภาษาอังกฤษ** ตามที่ทีมใช้จริง เช่น permission, endpoint, deploy, retest — ไม่แปลแบบฝืน ("จุดปลายทาง") และไม่เขียนอังกฤษล้วนทั้งประโยคเมื่อไม่จำเป็น
2. **ไม่ใส่คำลงท้าย** (ครับ, ค่ะ, นะคะ) ทุกที่ ทั้งใน chat และงานเขียน
3. **ประโยคสั้น 1 ประโยค 1 เรื่อง** และเว้นวรรคระหว่างวลี เพราะภาษาไทยไม่เว้นวรรคระหว่างคำ ประโยคยาวติดกันจะอ่านยากและตัดบรรทัดไม่ได้ในสไลด์หรือ UI
4. **ใช้คำที่คนอ่านเห็นจริง** — ชื่อเมนู ปุ่ม และหน้าจอสะกดตามของจริง ส่วนชื่อเทคนิค (path, function, field) ใส่ใน `code`
5. **ตัวย่อที่คนอ่านอาจไม่รู้** อธิบายสั้น ๆ ครั้งแรก เช่น "UAT (ระบบทดสอบก่อนขึ้นจริง)" — ถ้าคนอ่านเป็น dev ไม่ต้อง
6. **ตัวเลขมีหน่วยและที่มา** ค่าที่ประเมินเองต้องบอกว่า "ประมาณ" หรือ "ประเมิน" พร้อมฐานที่ใช้คิด
7. **แยกข้อเท็จจริงกับข้อสันนิษฐาน** — สิ่งที่ยังไม่มีหลักฐานใช้คำว่า "น่าจะ" หรือ "ยังไม่ยืนยัน"
8. **ไม่เดา** — ข้อมูลที่ไม่รู้ใส่ `[ยังไม่ทราบ: …]` แทนการแต่งค่าที่ดูสมเหตุสมผลขึ้นมาเอง
9. **ไม่มีคำฟุ่มเฟือย** — ไม่เยินยอ ("คำถามดีมาก"), ไม่ทวนคำถาม, ไม่ขึ้นต้นด้วย "แน่นอน!" หรือ "ได้เลย!"
10. **ใช้คำเรียกสิ่งเดียวกันคำเดียวทั้งงาน** — ถ้าเรียก "role" แล้วไม่สลับไปใช้ "บทบาท" กลางงาน

## โครงพื้นฐาน (ใช้กับทุกประเภท)

- **บรรทัดแรกคือข้อสรุป** หรือสิ่งที่คนอ่านต้องรู้มากที่สุด
- รายละเอียดเรียงจากสำคัญมากไปน้อย
- **ปิดท้ายด้วยสิ่งที่ต้องทำต่อหรือต้องตัดสินใจ** (ถ้ามี)
- รายการที่ขนานกันใช้ bullet · เปรียบเทียบหลายมิติใช้ตาราง · ขั้นตอนใช้เลขลำดับ
- heading สั้น บอกว่าส่วนนั้นมีอะไร ไม่ใช่ประโยคโฆษณา

## ตามประเภทงาน

### คำตอบใน chat

- เปิดด้วยคำตอบตรง ๆ ถามสั้นตอบสั้น
- รายงานงานที่ทำ: **ทำอะไรแล้ว → ตรวจยังไง → เหลืออะไร** ถ้า test ไม่ผ่านหรือข้ามขั้นตอนไป ให้บอกตรง ๆ
- คำถามถึงผู้ใช้: 1 คำถาม 1 เรื่อง ตัวเลือกบอกผลที่ตามมาของแต่ละทาง และระบุตัวที่แนะนำ

### เอกสาร, slide, report (คนอื่นอ่าน)

- ระบุผู้อ่านก่อนเขียน แล้วปรับระดับ technical ตามนั้น
  - หัวหน้า/PO: ผลกระทบ, เวลา, ความเสี่ยง, สิ่งที่ต้องตัดสินใจ
  - dev: ต้นเหตุ, จุดที่ต้องแก้, วิธีทดสอบ
- slide: **1 สไลด์ 1 ประเด็น**, หัวสไลด์บอกข้อสรุป, ตัวเลขมีที่มา, รายละเอียดเทคนิคย้ายไป speaker notes
- ค่าที่ประเมินเองและสมมติฐาน ต้องเขียนให้เห็นบนหน้า ไม่ซ่อน

### การ์ด Linear

- โครงตาม `qa-bug-writer` และ `linear-testcase-writer`
- ภาษาตาม skill นี้

### TODO.md

- task ที่เสร็จแล้ว เขียนว่าทำอะไรไป**จริง**และตรวจยังไง ไม่ใช่สิ่งที่ตั้งใจจะทำ

### content บนหน้าจอ, ในระบบ, ในไฟล์

- **ทีมหรือโปรเจกต์มีมาตรฐานข้อความ UI อยู่แล้ว ใช้ของทีม** — ข้อด้านล่างใช้เฉพาะตอนที่ไม่มีมาตรฐาน
- ข้อความบน UI: บอก **สิ่งที่เกิด + ผู้ใช้ทำอะไรต่อได้** และไม่โชว์ error code ดิบให้ผู้ใช้ปลายทาง
- ข้อความ error ต้องตรงกับหน้าที่ผู้ใช้อยู่ ห้าม copy ข้อความจากหน้าอื่นมาใช้
- คำเรียกเมนู ปุ่ม และสถานะ ต้องตรงกันทั้งระบบ

- [ ] ไทยเป็นหลัก ศัพท์ technical อังกฤษ ไม่มีประโยคอังกฤษล้วนที่ไม่จำเป็น
