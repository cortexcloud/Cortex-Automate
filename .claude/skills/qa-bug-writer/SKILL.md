# QA Bug Writer

เขียนการ์ด bug ให้ **ใครอ่านก็เข้าใจทันที** (PO, dev, QA คนอื่น) ว่า **ปัญหาคืออะไร เกิดที่ไหน และแสดงอาการแบบไหน** — แล้วค่อยให้รายละเอียดทางเทคนิคสำหรับ dev แยกไว้ท้าย

หลักคิดเดียวกับการตั้งชื่อ Test Case ใน `linear-testcase-writer` ("ตรวจสอบอะไร + ที่ไหน + เงื่อนไขอะไร") — แต่สำหรับ bug คือ "เกิดปัญหาอะไร + ที่ไหน + อาการเป็นอย่างไร"

> **สไตล์ภาษา**: ตาม skill `plain-writing-th` (`.claude/skills/plain-writing-th/SKILL.md`) — skill นี้กำหนดเฉพาะ **โครงการ์ด bug** ถ้าเรื่องภาษาขัดกัน ให้ยึด `plain-writing-th`

## ขั้นตอน

1. รวบรวมข้อมูลจริงจากผลทดสอบก่อนเขียน: steps ที่ทำ, ค่าที่กรอก, ข้อความ error ที่เห็นบนจอ, HTTP status/endpoint (ถ้ามี), รูป ①②③ + วิดีโอ, จำนวนครั้งที่เกิดซ้ำ, วันเวลา, env, user, version — **ห้ามเติมข้อมูลที่ไม่มีหลักฐาน**
2. ถาม/ยืนยันกับผู้ใช้ก่อนสร้างจริง: แบ่งการ์ดอย่างไร (1 TC = 1 bug หรือรวม bug ที่ error เดียวกัน), วางใต้การ์ดไหน, template, assignee, severity
   - ก่อนสร้างการ์ดจริงทุกครั้ง **ต้องถามชื่อคนที่จะเป็น assignee จากผู้ใช้ก่อนเสมอ** ห้ามเดา ห้ามคัดลอกจากการ์ดแม่ และห้ามปล่อยว่างเองโดยไม่ถาม · เช็คบัญชีที่ Linear connector ใช้ด้วย `get_user("me")` แล้วแจ้งผู้ใช้ว่าการ์ดจะขึ้นชื่อผู้สร้างเป็นใคร ถ้าไม่ใช่ตัวผู้ใช้ให้หยุดถามก่อน เพราะชื่อผู้สร้างแก้ทีหลังไม่ได้
3. ตั้งชื่อตาม **สูตรชื่อการ์ด**
4. เขียนเนื้อหาตาม **โครง body** และ **สไตล์ภาษา**
5. รัน **checklist** ก่อนส่ง
6. หลังสร้าง: ตรวจด้วยการอ่านการ์ดกลับ (`get_issue`) — response ตอนสร้าง/แก้อาจเป็นค่าเก่า, ใส่ลิงก์ bug กลับไปที่การ์ด TC ต้นทาง, สรุปรายการ bug ที่การ์ดแม่ถ้ามี

## วางการ์ดไว้ที่ไหน (เทียบ scope กับ AC ก่อน)

- อ่าน AC ของการ์ด requirement ก่อนวางการ์ด bug
- **อยู่ใน AC** → เป็น sub-issue ของการ์ด requirement (`parentId`)
- **นอก AC** (เจอระหว่างทดสอบแต่ไม่ใช่สิ่งที่การ์ดนี้ทำ) → สถานะ Triage ไม่มี parent + relation `relatedTo` การ์ด requirement และ TC ต้นทาง
- ไม่แน่ใจ → ถามผู้ใช้พร้อมเหตุผลราย bug · ย้ายเข้า Triage แล้วอ่านกลับ เพราะระบบอาจเปลี่ยน priority เอง
- ตัวอย่าง SBH-1198 (check pdx / sex): SBH-3351 / 3352 อยู่ใน AC = sub-issue · SBH-3353 (แถวหาย) / 3184 (กดสร้างหลายรอบ) / 3185 = นอก AC → Triage

## Severity (มาตรฐานทีม QA · 9 พ.ย. 2569)

ใช้กับ bug จากงาน Test in cycle (CT), Regression (RG) และ Master data · **ไม่ใช้กับ Pentest** — Pentest ใช้ severity / CVSS จาก report ต้นฉบับตาม skill `pentest-workflow`

| Severity | ความหมาย |
| -- | -- |
| Critical | ระบบหรือ Core Flow ใช้ต่อไม่ได้ ข้อมูลเสียหาย กระทบความปลอดภัยผู้ป่วย หรือเงินรั่วไหล (Financial Leakage) · รวมถึงข้อมูลที่ส่งออกนอกระบบผิด เช่น ยอดเงิน รหัส หรือวันเวลาในไฟล์ส่งเบิก |
| High | ฟังก์ชันหลักพัง ไม่มีทางเลี่ยงที่ดี |
| Medium | ฟังก์ชันพังบางส่วน มีทางเลี่ยง |
| Low | เรื่องเล็ก เช่น UI หรือข้อความ |

นิยามเดียวกับชีต Lists Guide และ Regression Plan ในไฟล์ Regression (`docs/TMH_Regression_v2.9.0_Final.xlsx`) — แก้ที่หนึ่งต้องแก้อีกที่ให้ตรงกัน

- **ฟังก์ชันหลัก** = ทุก step ใน Scenario ของชีต E2E core flow · ถ้าไม่อยู่ใน E2E core flow ให้นับเป็นฟังก์ชันหลักเมื่อตอบ "ใช่" ข้อใดข้อหนึ่ง: (1) ถ้าใช้ไม่ได้ ผู้ใช้ทำงานหลักของ Module ไม่จบ (2) คนไข้ทุกรายหรือเกือบทุกรายต้องผ่านจุดนี้ (3) ผลลัพธ์ถูกส่งต่อไปใช้งานจริง เช่น Order ไปห้องยา ไฟล์ส่งเบิกไป สปสช. · ไม่ใช่ฟังก์ชันหลัก: Filter, Sort, Export รายงาน, การแสดงผลเสริม
- ประเมินจากผลต่อผู้ใช้ ผู้ป่วย หรือโรงพยาบาล **ไม่ใช่จากต้นเหตุ** — bug จาก master data ก็เป็น Critical ได้ (เช่น ยาไม่มีราคาตามสิทธิ แล้วไม่เกิด claim)
- ประเมินจากกรณีแย่ที่สุดที่เกิดได้จริง แล้วเขียนเหตุผลสั้น ๆ เป็นภาษาผู้ใช้ไว้ใต้บรรทัด Severity (`* Remark:`) · ถ้ายังไม่ได้ตรวจสิ่งที่จะเปลี่ยนระดับ (เช่น ไฟล์ Export) ให้เขียนว่ายังไม่ได้ตรวจ และระดับจะเปลี่ยนเป็นอะไรถ้าผลออกมาอีกแบบ
- **กฎ TOR:** bug ที่ได้ Medium / Low แต่อยู่ในงานที่ TOR = Yes → Priority อย่างน้อย High · **ไม่เปลี่ยน Severity** · เขียนใน Remark ว่าอยู่ใน TOR
- **ใครตั้ง:** QA ตั้ง Severity ในเนื้อการ์ด → PO จัด Priority (ช่อง Priority ของ Linear) · QA ใส่คำว่า "QA แนะนำ" หรือ "QA ประเมินเบื้องต้น" และฝาก PO ยืนยันใน Remark · ไม่ต้องตั้งช่อง Priority เอง เพราะย้ายเข้า Triage แล้วระบบอาจเปลี่ยนเอง

แยกตามประเภทงาน (แต่ละงานมีเงื่อนไขของตัวเอง ห้ามใช้แบบเดียวกันทั้งหมดโดยไม่ดูประเภทงาน):

| | Test in cycle (CT) | Regression (RG) | Master data |
| -- | -- | -- | -- |
| Severity ในการ์ด | ✅ | ✅ | ✅ |
| Impact | — | ✅ กรอกในชีต E2E core flow: Extensive (ทั้งโรงพยาบาล / หลายแผนก) · Significant (ผู้ใช้จำนวนมากใน Module) · Moderate (บางกลุ่ม / บางเคส) · Minor (น้อยมาก) | — |
| Priority | PO ตั้ง | Excel คำนวณ Bug Priority = Severity × Impact และยกเป็น High ตามกฎ TOR อัตโนมัติ (ดู TOR จากชีต Cards) | ไม่ใส่ (ตามรูปแบบ COR-4715) |
| กฎ TOR | เขียนใน Remark | สูตร Excel ทำให้ | เขียนใน Remark |
| รูปแบบการ์ด | skill นี้ | ตามการ์ดตัวอย่าง COR-4722 + ใส่ Defect ID ในไฟล์ Regression | ตามการ์ดตัวอย่าง COR-4715 |

## สูตรชื่อการ์ด

```
[Bug][<Module>][<Form/Feature>] - <ทำอะไร> ใน <ที่ไหน> แล้ว <อาการที่ผู้ใช้เห็น>
```

- **ทำอะไร** = กิจกรรมที่ผู้ใช้ทำตอนเจอปัญหา (กด Save, เพิ่มค่าใช้จ่าย, แก้ Dx)
- **ที่ไหน** = หน้าจอ/tab/form ที่ผู้ใช้รู้จัก (Safety Checklist ใน Operation Detail)
- **อาการ** = สิ่งที่ผู้ใช้เห็นหรือผลกระทบ (ข้อมูลไม่ถูกบันทึก, ปุ่มหมุนค้าง, ขึ้นข้อความ error)
- ใช้ภาษาไทยเป็นหลัก ชื่อเมนู/ปุ่มให้สะกดตามหน้าจอจริง
- ข้อความ error บนจอใส่ในชื่อได้ถ้าสั้นและช่วยค้นหา — แต่ **ไม่ใส่ status code / endpoint ในชื่อ**

| ❌ ไม่ดี | ✅ ดี |
| -- | -- |
| กด Save แล้วไม่บันทึก (412 ที่ ehrbase contribution) ไม่มี error บน UI | กด Save ใน Safety Checklist (Operation Detail) แล้วข้อมูลไม่ถูกบันทึก และไม่มีข้อความแจ้งเตือน |
| Add charge failed surgical operation detail input invalid | เพิ่มค่าใช้จ่ายใน OR Charges ไม่ได้ ขึ้นข้อความ "surgical operation detail input invalid" |
| Post-anesthesia bug | กด Save ใน Post-anesthesia แล้วปุ่มหมุนค้าง ข้อมูลไม่ถูกบันทึก |

## โครง body (ตาม template QA Bug)

คงหัวข้อของ template ไว้ครบตามลำดับ แล้วเขียนเนื้อหาแต่ละส่วนแบบนี้:

```
# Test Result

### 1. Description:
* User / Env / Version / Date/Time / Severity (+ เหตุผลสั้น ๆ เป็นภาษาผู้ใช้)
* etc.,: OR / HN / ข้อมูลอ้างอิงอื่น
* TC ต้นทาง: <ลิงก์การ์ด TC>

### 2. Steps reproduce:
1. ... (ทีละขั้น ระบุเมนูที่กด ค่าที่กรอกจริง เช่น สินค้า "Adrenaline" จำนวน 1)
n. ขั้นที่เห็นปัญหา (เช่น Reload แล้วเปิดหน้าเดิม)

### 3. Actual Result:
* ปัญหา: <1 ประโยค ว่าเกิดอะไรขึ้น>
* เกิดที่: <Module › Tab › Form>
* อาการ: <ผู้ใช้เห็นอะไร ผู้ใช้จะเข้าใจผิดอย่างไร ผลกระทบคืออะไร>
* เกิดซ้ำ: <กี่รอบ / ทุกครั้งหรือไม่>
* ข้อสังเกต: <สิ่งที่เห็นจริงที่ช่วยไล่ปัญหา เช่น form เดียวกันอีกฝั่งบันทึกได้> (ถ้ามี)

① ก่อนกด ... — รูป
② หลังกด ... — รูปที่เห็นปัญหา
③ หลัง Reload — รูปที่ยืนยันผล
🎬 วิดีโอทั้ง flow

**รายละเอียดสำหรับ dev**
* request ที่ล้มเหลว: `<status> <METHOD> <endpoint>`
* ข้อความ error ฉบับเต็ม (ถ้ามี)
* สิ่งที่ต้องให้ dev ยืนยัน (ถ้ามี) — เขียนเป็นคำถาม ไม่ใช่ข้อสรุป

### 4. Expected Result:
* สิ่งที่ควรเกิด เป็นภาษาผู้ใช้ (บันทึกสำเร็จ / reload แล้วข้อมูลยังอยู่ / ถ้าบันทึกไม่ได้ต้องแจ้งผู้ใช้)
```

## สไตล์ภาษา

- **เล่าจากมุมผู้ใช้ก่อน** — "กด Save แล้วหน้าจอไม่แจ้งอะไรเลย ผู้ใช้จะเข้าใจว่าบันทึกแล้ว แต่ reload แล้วค่าหาย" ดีกว่า "contribution 412, silent fail"
- **ประโยคสั้น 1 ใจความ** ต่อ bullet
- **ศัพท์ technical** (status code, endpoint, composition, payload, graphql) → ย้ายไปหัวข้อ "รายละเอียดสำหรับ dev" เสมอ ห้ามตัดทิ้ง เพราะ dev ต้องใช้
- คำที่คนทั่วไปไม่รู้จัก เช่น "silent fail", "toast" → เขียนเป็นภาษาธรรมดา ("ไม่มีข้อความแจ้งเตือน", "ขึ้นข้อความแจ้งเตือนมุมจอ")
- ข้อความ error ที่ระบบแสดง ให้คัดลอกตามจริงในเครื่องหมายคำพูด ห้ามแปล/ย่อจนความหมายเปลี่ยน
- **ห้ามเดาสาเหตุ** — ถ้ายังไม่ยืนยัน ให้เขียนเป็น "ต้องให้ dev ยืนยันว่า ..." ห้ามใช้ "น่าจะเพราะ ..." / "มักเกิดจาก ..." เป็นข้อสรุป
- Severity ให้เหตุผลเป็นผลกระทบต่อผู้ใช้ (ข้อมูลหายโดยไม่รู้ตัว / เพิ่มค่าใช้จ่ายไม่ได้) ไม่ใช่เหตุผลทางเทคนิค

### ตัวอย่าง Actual Result

❌ technical เกิน:
```
* กด Save แล้ว request contribution ได้ 412 Precondition Failed
* UI ไม่แสดง error (silent fail)
```

✅ อ่านง่ายและครบ:
```
* ปัญหา: เปลี่ยนคำตอบใน Safety Checklist แล้วกด Save ข้อมูลไม่ถูกบันทึก
* เกิดที่: OR case › Operation Detail › Safety Checklist
* อาการ: กด Save แล้วหน้าจอไม่แจ้งอะไรเลย ผู้ใช้จะเข้าใจว่าบันทึกแล้ว แต่พอ reload คำตอบกลับเป็นค่าเดิม
* เกิดซ้ำ: ทุกครั้งที่ลอง (2 รอบ)

รายละเอียดสำหรับ dev
* request ที่ล้มเหลว: `412 POST /ehrbase/rest/openehr/v1/ehr/{ehr_id}/contribution`
```

## สรุปรายการ bug ที่การ์ดแม่

ตาราง 1 แถวต่อ bug: `# | Bug card | ที่ไหน (Tab > Form) | อาการ (ภาษาผู้ใช้ 1 ประโยค) | Severity | TC ต้นทาง` + ลิงก์ผลทดสอบเต็ม + สิ่งที่ไม่ได้รวมเป็น bug พร้อมเหตุผล

## Checklist ก่อนส่ง

- ทุกข้อเท็จจริงมาจากรายการที่ทดสอบจริง — ข้อมูลของผู้ป่วย / record อื่นห้ามเขียนเหมือนเป็นของรายนี้ (เช่น ค่า API ของผู้ป่วยรายอื่น) ถ้ายังไม่ได้เช็คให้เขียนว่า "ยังไม่ได้เช็ค"
- อาการที่เขียนต้องทำจริงจนเห็น (เห็นแค่ tag ยังไม่พอ ต้องกดแล้วดูค่า)
- เลข TC ในเนื้อความครอบด้วย backtick (`TC-SBH-1198-012`) — ไม่งั้น Linear แปลงส่วน SBH-1198 เป็นลิงก์
- วางการ์ดตาม scope ของ AC แล้ว (sub-issue หรือ Triage)
- Severity ตรงตามนิยามในหัวข้อ Severity ของประเภทงานนั้น · มี Remark บอกเหตุผล + ฝาก PO ยืนยัน · ระบุ TOR ถ้างานอยู่ใน TOR
- ชื่อการ์ดบอกครบ ทำอะไร + ที่ไหน + อาการ และไม่มี status code / endpoint
- Actual Result มี ปัญหา / เกิดที่ / อาการ / เกิดซ้ำ ครบ
- คนที่ไม่ใช่ dev อ่าน 3 บรรทัดแรกของ Actual Result แล้วเข้าใจว่าเกิดอะไร
- รายละเอียด technical ยังอยู่ครบในหัวข้อสำหรับ dev
- Steps ทำตามได้จริงโดยไม่ต้องถาม (มีเมนู ค่าที่กรอก จุดที่เห็นปัญหา)
- มีรูป ①②③ + วิดีโอ และลิงก์ TC ต้นทาง
- ไม่มีการเดาสาเหตุเป็นข้อสรุป
